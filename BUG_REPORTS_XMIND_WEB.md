# Bug Reports: MindMap vs XMind Web

Дата проверки: 2026-10-10  
Эталон: XMind Web (`https://app.xmind.com/`)  
Проверяемый проект: локальный MindMap (`http://localhost:5173`)

> Desktop XMind в этой проверке не учитывался.

## Краткое резюме

Самые серьёзные расхождения сейчас находятся в области drag and drop, раскладки и поведения веток. Визуальная оболочка частично похожа на XMind Web, но DnD-модель работает иначе: перетаскивание основной ветки на пустое место превращает её в floating topic, баланс карты фактически не работает, зоны попадания зависят от масштаба и имеют резкие пороги.

Автотесты проекта на момент проверки проходили (`typecheck`, `vitest`, `e2e`), но они покрывают happy path и не ловят эти UX-регрессии.

## DND-001: Переключатель "Баланс карты" не влияет на раскладку

**Приоритет:** P1  
**Область:** Layout / Format panel / Map settings  
**Файл:** `frontend/src/editor/layout.ts`

### Шаги

1. Открыть карту с несколькими основными ветками, одна из которых значительно выше остальных.
2. Открыть панель `Формат -> Карта`.
3. Переключить `Баланс карты` вкл/выкл.
4. Сравнить координаты/расположение основных веток.

### Фактический результат

Положение тем не меняется вообще. Проверка координат при `balance: true`, `balance: false`, затем снова `balance: true` дала одинаковый результат.

### Ожидаемый результат

Как в XMind Web: баланс карты должен реально перераспределять основные ветки по сторонам/высоте и менять раскладку.

### Вероятная причина

В `layoutSheet` значение принудительно сбрасывается:

```ts
BALANCE = false
```

То есть настройка из `sheet.balance` не используется.

## DND-002: Перетаскивание основной ветки на другую сторону превращает её в floating topic

**Приоритет:** P0  
**Область:** Drag and drop / Mind map structure  
**Файлы:** `frontend/src/editor/MapCanvas.tsx`, `frontend/src/editor/store.ts`

### Шаги

1. Открыть карту Mind Map с центральной темой и несколькими main topics.
2. Перетащить основную ветку с правой стороны на левую сторону холста.
3. Сравнить с XMind Web: там такая операция переносит ветку на другую сторону карты.

### Фактический результат

В MindMap тема удаляется из `rootTopic.children` и попадает в `floatingTopics`.

### Ожидаемый результат

Как в XMind Web: ветка должна остаться основной веткой центральной темы, только сменить сторону/позицию в раскладке. Связь с центральной темой должна сохраниться как структурная ветка, а не как floating topic.

### Вероятная причина

Если `d.target` не найден, код вызывает `detach`, а `detach` всегда превращает child topic в floating topic:

```ts
if (ids.length === 1 && one?.kind === 'floating') ed().setPosition(ids[0], pos)
else ed().detach(ids, pos)
```

## DND-003: Свободное положение веток работает через скрытый offset и ведёт себя не как XMind Web

**Приоритет:** P0  
**Область:** Free branch positioning / Drag and drop  
**Файлы:** `frontend/src/editor/MapCanvas.tsx`, `frontend/src/editor/layout.ts`

### Шаги

1. Включить `Формат -> Карта -> Свободное положение веток`.
2. Перетащить обычную ветку на пустую область холста.
3. Проверить модель документа.

### Фактический результат

Тема остаётся в прежнем месте дерева, но получает поле `offset`. Визуально ветка сдвигается, однако модель структуры не меняется.

### Ожидаемый результат

Поведение должно соответствовать XMind Web: свободное позиционирование ветки должно быть управляемым, предсказуемым и не конфликтовать с обычным переносом ветки между сторонами/родителями. Пользователь должен понимать, останется ли ветка структурной, станет floating или просто изменит свободную позицию.

### Вероятная причина

При `sheet.freeBranch` код перехватывает drop на пустом месте и пишет `offset`:

```ts
if (sheet.freeBranch && ids.length === 1 && one?.kind === 'child') {
  const prev = one.topic.offset ?? { x: 0, y: 0 }
  ed().setTopic([ids[0]], { offset: { x: prev.x + d.cur.x - d.start.x, y: prev.y + d.cur.y - d.start.y } })
  return
}
```

## DND-004: Один и тот же экранный drag даёт разные результаты при разных масштабах

**Приоритет:** P0  
**Область:** Drag hit-testing / Zoom  
**Файл:** `frontend/src/editor/MapCanvas.tsx`

### Шаги

1. Открыть карту с темами `A`, `B`, `C`.
2. Установить zoom `50%`.
3. Перетащить `C` и отпустить примерно в 30 экранных пикселях от `B`.
4. Повторить тот же сценарий при zoom `100%` и `200%`.

### Фактический результат

Одинаковый экранный жест даёт разные операции:

- zoom `0.5`: тема становится floating;
- zoom `1`: тема становится ребёнком `B`;
- zoom `2`: тема становится ребёнком `B`.

### Ожидаемый результат

Зоны DnD должны ощущаться одинаково при любом масштабе. Пользователь не должен получать другой тип операции только из-за zoom.

### Вероятная причина

Hit-test считается в world coordinates, а порог `40` тоже задан в world-px:

```ts
if (dist < 40 && (!best || dist < best.dist)) best = { box, dist }
```

Порог должен быть нормализован относительно zoom или считаться в screen coordinates.

## DND-006: Вставка before/after ловится только внутри прямоугольника темы

**Приоритет:** P1  
**Область:** Reorder siblings / Drag and drop  
**Файл:** `frontend/src/editor/MapCanvas.tsx`

### Шаги

1. Перетащить тему между двумя соседними темами.
2. Отпустить в промежутке между ними, не попадая строго внутрь box темы.

### Фактический результат

Если курсор не внутри box темы, `findDropTarget` возвращает режим `child`, а не `before/after`, либо вообще не находит target и тема становится floating.

### Ожидаемый результат

Как в XMind Web: drop между соседями должен переставлять тему между ними, с явным insertion indicator.

### Вероятная причина

Режим `before/after` вычисляется только если точка находится внутри box темы:

```ts
if (!ref.parent || best.dist > 0 || ref.kind !== 'child') return { id: box.id, mode: 'child' }
```

## DND-007: Drop target определяется по точке курсора, а не по dragged topic/ghost

**Приоритет:** P1  
**Область:** Drag and drop / UX  
**Файл:** `frontend/src/editor/MapCanvas.tsx`

### Шаги

1. Схватить тему не за центр.
2. Навести визуальный ghost темы на целевую тему так, чтобы курсор оставался сбоку.
3. Отпустить.

### Фактический результат**

Операция может не сработать как ожидается, потому что target ищется по `cur`, то есть по точке курсора.

### Ожидаемый результат

Drop должен учитывать положение dragged topic/ghost и его пересечение с потенциальными targets, а не только курсор.

### Вероятная причина

```ts
updateDrag({ ...d, cur, active, target: active ? findDropTarget(cur, d.ids) : null })
```

## DND-011: Мультивыделение и detach потенциально нестабильны из-за удаления siblings по старым индексам

**Приоритет:** P1  
**Область:** Multi-select drag / Data consistency  
**Файл:** `frontend/src/editor/store.ts`

### Шаги

1. Выделить несколько sibling-тем.
2. Перетащить их на пустое место.

### Фактический результат**

В простом проверенном сценарии `B + C` корректно стали floating topics. Но реализация опасная: массив siblings изменяется во время итерации, а индексы берутся из старого `indexSheet`.

### Ожидаемый результат**

Удаление нескольких элементов из одного массива должно идти стабильно: например, по индексам в обратном порядке или через фильтрацию.

### Вероятная причина

```ts
moving.forEach((id, i) => {
  const l = locate(sh, id)!
  l.siblings.splice(l.index, 1)
  ...
})
```

После первого `splice` индексы следующих siblings меняются.

## UI-009: Picker-меню в панели "Формат" обрезаются правой панелью

**Приоритет:** P1  
**Область:** Format panel / Dropdowns  
**Файлы:** `frontend/src/editor/FormatPanel.tsx`, `frontend/src/styles/app.css`

### Шаги

1. Открыть локальный MindMap в окне примерно `900x620`.
2. Выбрать центральную тему.
3. Открыть `Формат -> Стиль`.
4. Открыть picker `Фигура`, `Структура` или `Форма линии`.

### Фактический результат

Выпадающий список рисуется внутри `.fp-scroll` / `.side-panel`, которые имеют `overflow: auto`.
Замер Playwright для picker структуры:

- viewport: `900x620`;
- `.fp-scroll`: `left=620`, `right=888`, `bottom=588`;
- `.picker-pop`: `left=608`, `right=868`, `top=592`, `bottom=952`.

То есть popup одновременно уходит левее видимой области панели и почти полностью ниже её нижней границы. Визуально список режется контейнером.

### Ожидаемый результат

Как в XMind Web: dropdown должен открываться отдельным слоем поверх интерфейса, не обрезаться панелью и переворачиваться/смещаться, если не помещается в viewport.

### Вероятная причина

`Picker` рендерит popup inline, без портала:

```tsx
<div className="picker-pop" ...>
```

CSS задаёт абсолютное позиционирование внутри панели:

```css
.picker-pop { position: absolute; right: 0; top: calc(100% + 4px); ... }
.fp-scroll { overflow: auto; }
```

## UI-010: В панели "Формат" смешаны кастомные picker'ы и нативные select'ы для одной функции

**Приоритет:** P2  
**Область:** Format panel / Dropdown consistency  
**Файл:** `frontend/src/editor/FormatPanel.tsx`

### Шаги

1. Выбрать тему.
2. Открыть `Формат -> Стиль -> Структура`.
3. Сравнить controls в секции.

### Фактический результат

В одной секции есть два разных способа выбора структуры:

- кастомный иконочный `Picker` в заголовке секции;
- нативный `<select aria-label="Структура">` внутри секции.

В `Формат -> Карта` карточка структуры тоже реализована через невидимый нативный `<select>`, растянутый поверх всей карточки:

```tsx
<select value={cur.id} aria-label="Структура карты" ...>
```

```css
.struct-card select { position: absolute; inset: 0; opacity: 0; cursor: pointer; }
```

### Ожидаемый результат

Как в XMind Web: выбор структуры должен быть единым custom dropdown/popup с предсказуемым внешним видом, иконками, hover/selected-состояниями и одинаковой логикой открытия.

### Почему это баг

Пользователь получает разные dropdown-модели для одного и того же действия: один список обрезается панелью, второй открывается как OS-native select, третий спрятан невидимым overlay. Это выглядит и работает нестабильно, особенно по сравнению с XMind Web.

## UI-011: Dropdown'ы панели формата не умеют позиционироваться относительно viewport

**Приоритет:** P1  
**Область:** Dropdown positioning / Responsive  
**Файлы:** `frontend/src/editor/FormatPanel.tsx`, `frontend/src/styles/app.css`

### Шаги

1. Открыть локальный MindMap в окне `700x520`.
2. Открыть `Формат -> Стиль`.
3. Открыть любой picker в правой панели.

### Фактический результат

Picker открывается с фиксированной шириной `260px`, но правая панель имеет видимую область около `268px` и внутренние padding/negative margins. Замер:

- `.fp-scroll`: `left=420`, `right=688`;
- `.picker-pop`: `left=408`, `right=668`.

Левая часть popup выходит за область прокрутки панели. Для нижних picker'ов popup также уходит ниже панели и не переворачивается вверх.

### Ожидаемый результат

Dropdown должен вычислять доступное место и выбирать позицию: left/right, up/down, либо рендериться через portal в `document.body`, как это уже сделано для общего `Dropdown` в `Chrome.tsx`.

### Вероятная причина

В отличие от `Dropdown` (`Chrome.tsx`), который рендерится через `createPortal` и clamp'ится в пределах окна, `Picker` не делает ни portal, ни viewport clamp.

## UI-012: Вложенные меню раскрываются только hover'ом и не имеют общей логики flip/clamp

**Приоритет:** P2  
**Область:** Main menu / Submenus / Dropdowns  
**Файлы:** `frontend/src/editor/Chrome.tsx`, `frontend/src/styles/app.css`

### Шаги

1. Открыть главное меню.
2. Навести на пункты с подменю: `Файл`, `Правка`, `Вид`, `Панель формата`.
3. Проверить поведение подменю мышью и клавиатурой.

### Фактический результат

Вложенное меню открывается при hover:

```tsx
<div className="submenu" onMouseEnter={() => setOpen(true)} onMouseLeave={() => setOpen(false)}>
```

Позиция подменю жёстко задана вправо:

```css
.menu.sub { position: absolute; left: calc(100% + 4px); top: -8px; }
```

У основного `Dropdown` есть portal и ограничение viewport, но у `.menu.sub` этой логики нет. Специальный flip реализован только для контекстного меню через `.ctx-menu.flip`, а не для обычного главного меню.

### Ожидаемый результат

Как в XMind Web: вложенные меню должны быть устойчивыми к краям окна, не зависеть только от hover, нормально работать с кликом/клавиатурой и не закрываться при мелком промахе курсора.

## UI-014: Поиск по Cmd/Ctrl+F открывает не search bar, а левую панель "Структура"

**Приоритет:** P1  
**Область:** Search / Navigation / Keyboard shortcuts  
**Файлы:** `frontend/src/pages/EditorPage.tsx`, `frontend/src/editor/SearchBar.tsx`, `frontend/src/editor/Chrome.tsx`

### Шаги

1. Открыть карту.
2. Нажать `Cmd+F` / `Ctrl+F`.
3. Проверить, появился ли отдельный поиск по карте.
4. Открыть `Меню -> Правка -> Поиск`.

### Фактический результат

После `Cmd+F`:

- `search-bar`: `0`;
- `nav-panel`: `1`;
- внутри `nav-panel` появляется поле `Найти`.

Компонент `SearchBar` существует, но не импортируется и не рендерится ни в одном месте приложения. Поиск из меню тоже ведёт в `ed.setNav('outline')`:

```tsx
<MenuItem label="Поиск" hint="⌘ F" onClick={() => { close(); ed.setNav('outline') }} />
```

### Ожидаемый результат

Как в XMind Web: поиск должен открывать понятный search UI, фокусировать поле поиска, подсвечивать найденные темы и позволять переходить по результатам. Если используется левый navigation search, пункт должен называться и вести себя именно как открытие навигационной панели, а не как отдельный поиск.

### Почему это баг

В проекте уже есть отдельный `SearchBar` с логикой `search.open`, счётчиком результатов и заменой, но пользователь не может его вызвать. Функциональность фактически мёртвая.
